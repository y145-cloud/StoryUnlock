# 剧情解锁 Story Unlock

给 SillyTavern / TauriTavern 用的**条件注入**扩展：用一句自然语言描述解锁条件，剧情变量（MVU）满足条件后，才把预设内容发给 AI。

你只需要写「当 user 在钟楼承认自己恢复记忆后」这样的条件；保存时扩展调用一次当前模型，把它转成 MVU 变量和判断条件。之后每轮不再额外判断，只读取 MVU。

典型用法：角色设定为「失忆」，当新建的 `剧情解锁.钟楼认罪` 变成 `true` 时，才把「失忆前的人设」注入给 AI；在那之前，这段内容完全不存在于上下文里。

- **不用世界书**：条件内容不写入、不读取世界书条目，不会在一张卡的不同聊天之间串味。
- **规则随聊天**：每个聊天有自己的解锁项、条件和注入内容；A 聊天改规则不影响 B 聊天。
- **状态也随聊天**：每个聊天独立保存解锁进度；新聊天默认空白，旧版角色卡规则会在老聊天首次打开时迁移一份。
- **纯前端**：不需要后端服务；适配 SillyTavern 与 TauriTavern。

---

## 1. 前置条件

1. 已安装 **SillyTavern** 或 **TauriTavern**。
2. 角色卡使用 **MVU（MagVarUpdate）**，并且 MVU 已经能正常把变量写进 AI 消息。
   - MVU 依赖「酒馆助手 / JS-Slash-Runner」；扩展本身不安装 MVU。
   - 本扩展读取的是每条 AI 消息里的 `variables[swipe_id].stat_data`，也会尝试调用 MVU 的 `Mvu.getMvuData()`；两者都没有时，变量列表会显示为空。
3. 当前聊天使用的模型能正常回复；保存自然语言条件时扩展会调用一次 `generateQuietPrompt`，如果该接口不可用，会自动回退成布尔变量。
4. 不需要安装任何世界书条目来配合本扩展。

> 说明：MVU 自己的初始变量可能仍来自角色卡里的 `[InitVar]`，那是 MVU 的机制；本扩展**不会**新增或修改世界书，也不会把解锁内容写进世界书。

## 2. 安装

### SillyTavern

把整个 `StoryUnlock` 文件夹放到：

```
<SillyTavern 目录>/public/scripts/extensions/third-party/StoryUnlock/
```

然后刷新酒馆页面，在「扩展」抽屉里找到 **剧情解锁 Story Unlock**。

> 不要覆盖已有的 `third-party` 目录，只新增 `StoryUnlock` 子目录。从 GitHub Release 下载的 zip 解压后目录通常叫 `StoryUnlock-0.3.0`，安装前请改名为 `StoryUnlock`。

### TauriTavern

TauriTavern 的扩展目录有两种，任选其一（local 优先）：

```
<数据目录>/default-user/extensions/StoryUnlock/
<数据目录>/extensions/third-party/StoryUnlock/
```

Windows 默认数据目录：

```
%APPDATA%/com.tauritavern.client/data
```

放好后重启/刷新 TauriTavern，在扩展设置里启用。

### 文件结构

```
StoryUnlock/
├── manifest.json      # 扩展声明
├── index.js           # 酒馆胶水层、设置面板、事件、斜杠命令
├── engine.js          # 纯函数：路径解析、条件判断、解锁状态、注入规划
├── settings.html      # 设置面板模板
├── style.css          # 面板与编辑器样式
├── package.json       # 仅用于本地 node 测试（type: module）
├── README.md
└── test/              # 引擎单测；运行扩展不需要
```

## 3. 快速上手（失忆人设示例）

1. 打开角色聊天，点扩展面板里的 **刷新变量**，确认 MVU 能读到变量。
2. 点 **新建解锁项**，在「简单」页填写：
   - 名称：`恢复失忆前的记忆`
   - 解锁条件（自然语言）：
     ```
     当 user 在钟楼承认自己恢复记忆后
     ```
   - 解锁后注入的内容：
     ```
     你其实记得失忆前的事：你曾是黄昏旅团的向导，名叫「澜」。
     你对「络络」有模糊的熟悉感，但暂时说不清原因。
     ```
   - 注入方式：`解锁后一直注入`（sticky）
3. 点 **AI 解析条件** 可以先看解析结果；点 **保存** 时也会自动解析。
   - 扩展会尽量复用已有 MVU 变量；
   - 没有合适的变量时，新建 `剧情解锁.xxx`；
   - 解析失败或模型不可用时，自动建一个布尔变量 `剧情解锁.su_xxx`，条件为 `== true`，规则仍然能保存。
4. 解析结果会以「变量维护说明」的形式在每次生成时发给主模型，让它在剧情里把变量改成 `true`。
   - 变量可能要到**下一轮** AI 更新后才出现在 MVU 面板；
   - 条件满足的那一次生成开始注入；
   - sticky 模式下，之后每楼都会带上这段内容；
   - 如果想让 AI 只“想起来一次”，把注入方式改成 **只注入一次**。
5. 想看下一次会发什么，点 **预览注入**；想手动控制，用规则卡上的 **解锁 / 锁定**。

> 自然语言条件写得越像“可观察的剧情事件”（谁、做了什么、达到什么结果），AI 越容易生成能维护的变量。比如「当 user 在钟楼承认自己恢复记忆后」就比「等剧情差不多了」可靠。

### AI 解析会做什么

保存时只调用**一次**当前聊天模型，要求它输出 JSON：

```json
{
  "variables": [
    { "path": "剧情解锁.钟楼认罪", "type": "boolean", "initial": false,
      "description": "当 user 在钟楼承认自己恢复记忆后设为 true" }
  ],
  "conditions": [
    { "path": "剧情解锁.钟楼认罪", "op": "==", "value": "true" }
  ],
  "match": "all",
  "explain": "新建布尔变量，在钟楼承认记忆时置为 true"
}
```

之后每轮生成，扩展会把变量定义和维护说明注入成 `<story_unlock_variables>`，让主模型按 MVU 的正常变量更新机制新增/维护变量；扩展自己只读 `stat_data` 判断条件，不再调用模型。手动点过「AI 解析条件」再保存会复用结果，不会重复调用；只有条件文本再次改动才会重新解析。

### 高级条件写法（一般不用改）

「高级」页保留原来的路径条件，适合你已经知道变量名、或想精确控制的情况。自然语言条件和高级条件是**二选一**：填了自然语言条件时，保存会以解析结果为准；清空自然语言条件才会使用高级条件。

路径从 MVU 的 `stat_data` 开始，不用写 `stat_data.` 前缀：

```
角色.络络.好感度
事件.失忆真相
剧情.章节
队伍[0].名字
```

支持点号、方括号和引号；也支持伪变量：

| 路径 | 含义 |
| --- | --- |
| `$floor` | 当前聊天楼层数（消息条数） |
| `$messageCount` | 同上 |
| `$lastMessage` | 最后一条 AI 消息文本 |
| `$lastUserMessage` | 最后一条用户消息文本 |
| `$chatName` | 当前角色/群聊名 |

运算符：`>= > <= < == != contains not_contains starts_with ends_with exists not_exists in not_in matches not_matches`。

- `exists` / `not_exists` 不需要填比较值。
- `in` / `not_in` 用逗号分隔列表，例如 `朋友,恋人`。
- MVU 叶子值如果写成 `[值, "说明"]`，比较时会自动取 `[0]`。

### 高级表达式

在「高级」页可以写 JS 表达式，和条件行是 **AND** 关系：

```js
get('角色.络络.好感度') >= 60 && get('事件.失忆真相') === true
```

可用参数：`stat_data`、`get(path)`、`value(path)`、`floor`、`msgCount`、`lastMessage`、`lastUserMessage`、`chatName`、`chat`。

表达式用 `new Function` 执行；只应写自己信任的规则，不要从不可信来源导入表达式。

### 注入方式

| 模式 | 行为 |
| --- | --- |
| `sticky` 解锁后一直注入 | 条件首次满足后永久解锁，之后每楼都注入；适合“恢复记忆/人设补全”。 |
| `once` 只注入一次 | 首次注入后不再注入；同一楼重新生成仍会注入，避免重 roll 丢失。 |
| `window` 解锁后限时注入 | 解锁后 N 楼内注入，之后停止；适合“短期状态/临时身份”。 |
| `while` 条件满足期间注入 | 条件为真时注入，条件变假就暂停；再次为真会恢复。 |

手动 **锁定** 会阻止自动解锁；**解锁** 会强制解锁（`sticky` 会一直生效，`once` 会在下一次生成注入）。

### 注入位置

默认：`IN_CHAT`，深度 `4`，角色 `System`，用 `<story_unlock>` 包裹。

- 多条命中时按「排序」从小到大拼接，每条带 `〔名称〕`。
- 包裹标题可以在「注入设置」里改；关掉包裹就只发正文。
- `IN_CHAT` 的深度越小越靠近最新消息；`IN_PROMPT` / `BEFORE_PROMPT` 是其他插入位置。
- 每次生成会先放 `<story_unlock_variables>`（让 AI 新增/维护变量），再放 `<story_unlock>`（已解锁的内容）；两段都没有时不会注入。

## 4. 多聊天隔离

这是本扩展和世界书方案的关键区别：**规则、变量定义、解锁状态都保存在聊天数据里**。

| 数据 | 保存位置 | 作用范围 |
| --- | --- | --- |
| 解锁项（自然语言条件、AI 解析出的变量定义、注入内容） | 当前聊天的 `chatMetadata.story_unlock_rules` | 只属于当前聊天 |
| 解锁状态（是否已解锁、注入次数、窗口起点） | 当前聊天的 `chatMetadata.story_unlock` | 只属于当前聊天 |
| MVU 变量当前值 | 当前聊天每条 AI 消息的 `variables` | 只属于当前聊天 |

因此：

- 同一张卡开 10 个聊天，每个聊天都可以有自己的一套解锁项；
- 在 A 聊天修改条件、注入内容或变量定义，不会影响 B 聊天；
- 每个聊天的解锁进度互不影响；
- 新聊天默认空白；旧版角色卡规则只会在“已经有 user 消息的老聊天”首次打开时自动复制一份；
- 不读取、也不写入世界书。

> 规则现在跟着聊天文件走：换设备时复制聊天文件即可保留；也可以随时用 **导出** 单独备份一套规则，再在另一个聊天里 **导入**（追加，不覆盖）。

## 5. 面板与斜杠命令

### 面板

- **启用**：总开关；关闭后生成前会清除注入。
- **新建解锁项**：默认只填名称、自然语言条件、注入内容、注入方式；路径条件收在「高级」。
- **AI 解析条件**：保存时自动执行；也可以在编辑器里手动点一次，先看解析出的变量和条件。
- **刷新变量**：重新读取当前聊天的 MVU 变量。
- **预览注入**：按当前状态计算下一次生成会发什么，并列出每条规则判定。
- **导入 / 导出**：JSON 规则备份；导入会追加并给重复 id 换新 id。
- **重置本聊天**：只清当前聊天的解锁状态，不删规则。
- 变量列表：点一行会把路径填进当前条件行（编辑器打开时），否则复制路径。
- 规则卡：测试条件、停用/启用、手动解锁、手动锁定、编辑。

### 斜杠命令

```
/su status              查看当前角色/聊天/楼层/规则状态
/su list                列出解锁项
/su test                测试所有规则条件
/su preview             预览下一次注入
/su var [路径]          查看 MVU 变量（不填路径列出前 50 条）
/su unlock <序号|名称>   手动解锁
/su lock <序号|名称>     手动锁定
/su reset yes           重置当前聊天解锁状态
```

别名：`/storyunlock`。

## 6. 常见问题

**Q：变量列表是空的？**
先确认 MVU 已经正常运行，并且当前聊天里至少有一条带 `variables` 的 AI 消息。点「刷新变量」；如果仍然为空，检查酒馆助手/MVU 版本。扩展会优先读 MVU API，失败时回退到消息里的 `stat_data`。

**Q：AI 解析失败/没有反应？**
解析需要当前聊天模型支持 `generateQuietPrompt`（酒馆助手/MVU 环境一般都有）。失败时扩展会自动建一个布尔变量 `剧情解锁.su_<id>` 作为兜底，规则仍然保存；你可以在「高级」页手动改条件，或稍后重试解析。解析不会在每轮生成时重复调用。

**Q：为什么新建的变量在 MVU 面板里还没出现？**
变量定义已经写进规则的注入文本，但真正的值要等主模型按维护说明执行一次 MVU 更新；通常是**下一轮**才出现。可以在「预览注入」里确认变量说明已经带上；如果一直不出现，检查角色卡是否允许 AI 新增变量，或改成一个已存在的变量。

**Q：每轮都发 `<story_unlock_variables>`，会不会很占 token？**
会占一点，但只包含启用规则的变量定义（最多 24 个、超长会截断），比每轮调用一次模型便宜。规则都手动锁定/停用后，这段会消失。

**Q：条件明明满足了，为什么没有注入？**
- 规则是否启用；
- 是否被手动锁定；
- 条件是否在**生成前**已经写入 MVU（MVU 通常根据上一条 AI 消息更新，条件生效可能比剧情晚一楼）；
- 打开「预览注入」看每条规则的 reason；
- 生成事件是否被其他扩展/斜杠命令中止（本扩展挂在 `GENERATION_AFTER_COMMANDS`）。

**Q：为什么 `once` 在同一楼重新生成还会注入？**
这是有意设计：同一楼重 roll 不应该丢掉刚刚解锁的内容；只有楼层前进后才停止。

**Q：两个字符串的数组为什么被当成 `[值, 说明]`？**
MVU 的叶子值约定是 `[值, "说明"]`，所以恰好两个字符串的数组会被解包成第一个元素。需要保留列表时，改成三个元素，或用 `标签[1]` / 高级表达式读取。README 这里特意标注，避免误判。

**Q：会不会写世界书？**
不会。扩展不调用世界书写入接口，也不创建世界书条目；解锁项和解锁状态只存在于当前聊天文件和注入文本里。

**Q：换聊天/换设备后规则还在吗？**
规则在当前聊天文件里，换聊天就是另一套，不会串；换设备时复制聊天文件即可，也可以先导出再导入。

**Q：支持群聊吗？**
支持。群聊也按当前聊天隔离，同一个群的不同聊天互不影响。

**Q：会不会增加很多 token？**
`sticky` 会把内容持续放进上下文，确实占 token；内容越长越明显。可以改用 `once` / `window`，或缩短注入文本。

## 9. 已知限制

- 解锁判断发生在生成前；不会追溯修改已经生成的消息。
- 自然语言解析需要一次模型调用（只在保存/手动解析时）；解析质量取决于当前模型和已有 MVU 变量。
- 新变量能否真正写进 MVU，取决于主模型是否按维护说明执行更新；扩展不会直接篡改 MVU 数据，也不写世界书。
- 变量可能要到条件满足后的下一轮才出现在 `stat_data`，因此解锁可能比剧情晚一楼。
- 如果 MVU 没有把变量写进消息，扩展只能显示空变量；这是 MVU 侧的问题。
- 旧版规则只迁移到“已有 user 消息的老聊天”；新聊天不会自动继承，需要的话用导出/导入复制一套。
- 高级表达式使用 `new Function`，只应使用可信规则。
- 本扩展会注入变量维护说明，但变量最终是否变化仍由主模型和 MVU 的更新机制决定；扩展不会直接写入或替换 MVU 数据。
